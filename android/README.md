# Android app (Google Play) — Royal Billiard 8

A Capacitor shell: the light web build (`tools/build_android.sh` → `android/www/`, ~39 MB, **no HD pack, no real-money card buttons**) runs in an Android WebView and talks to the game server (`CONFIG.server`, Render). Package name: `com.royalbilliard8.app`.

## Build the .aab (Play needs an App Bundle)
The Android SDK cannot be downloaded in the coding sandbox, so the bundle is built by GitHub Actions: **Actions → "Android app (Play Market)" → Run workflow** (set `version_code` 1, 2, 3 ... for every upload). When it finishes, download `royal-billiard-8-aab` from the bottom of the run.
Locally (Node 22, JDK 21, Android SDK): `bash tools/build_android.sh && cd android && npm install && npx cap add android && npx capacitor-assets generate --android --iconBackgroundColor '#0b1030' && npx cap sync android && cd android && ./gradlew bundleRelease`.

## Signing (once)
Play needs a signed bundle (Play App Signing keeps the real key, you upload with an *upload key*). Make the upload keystore once and KEEP it (lose it = ask Google to reset the upload key):
`keytool -genkeypair -v -keystore upload.jks -alias upload -keyalg RSA -keysize 2048 -validity 10000`
Then add 4 repository secrets (Settings → Secrets and variables → Actions): `ANDROID_KEYSTORE_BASE64` (`base64 -w0 upload.jks`), `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`. Never commit the keystore or the passwords. Without the secrets the workflow builds an unsigned bundle (testing only).

## Play Console checklist
- App: name *Royal Billiard 8*, game, free; privacy policy URL: `https://billiard8.onrender.com/privacy`; data deletion: `/data-deletion`.
- Content rating questionnaire, Data safety form (name, avatar, country, game results, user id; voice chat is not recorded), target audience 13+ / adults (not "for children": the game has chat and coins).
- Real-money items: Google Play requires **Google Play Billing** for digital goods inside the app, so the app has no card buttons (`CARD_PAY=false`) and sells ONLY the six 💎 packs through it; everything else costs 💎 (see "Google Play Billing" below). AppLovin MAX (rewarded video, interstitial) is a later step (plug the SDK into the `Y8` ad hooks: `y8Rewarded`, `y8StartAdOk`); until then the app shows no "watch ads" buttons.
- **Microphone (voice chat).** The manifest Capacitor generates has only `INTERNET`, so the WebView could not use the microphone at all (the lobby voice room and the in-match 🎤 would show "no permission"). The workflow now adds `RECORD_AUDIO` + `MODIFY_AUDIO_SETTINGS` after `npx cap add android`; Android asks the player once and the game keeps the microphone open between matches (`MicHub`). In the **Data safety** form answer *Audio → Voice or sound recordings*: collected = yes, processed ephemerally (heard live by the other player, never stored), not shared with third parties, optional. Needs a new bundle (`version_code` higher than the last upload).
- **minSdk 24.** Play's "automatic protection" (on by default for new apps) rejects a bundle with minSdk below 24 ("Для автоматической защиты ... SDK 24"); an old Capacitor 6 shell used 22. **Play also requires target API 36** (the console says "целевой уровень API должен быть не ниже 36"), so the shell is **Capacitor 8** (compile / target SDK 36, minSdk 24, AGP 8.13, Gradle 8.14, needs **Node 22 and JDK 21** - the workflow uses them). Its SystemBars plugin pads the WebView by the system bars (or hands the insets to the page as `env(safe-area-inset-*)` when the page has `viewport-fit=cover`, as the game does) because Android 15+ draws apps edge to edge.
- **Always landscape, full screen.** First test on a phone (portrait WebView + status / navigation bars): the game rotated itself inside the portrait window, the login panel was squeezed to an edge, the clock / antenna stayed on screen. Now the workflow sets `screenOrientation="sensorLandscape"` on the activity (no rotation hack in the app), `SystemBars.hidden: true` in `capacitor.config.json` (bars hidden; a swipe from the edge shows them for a moment), `windowLayoutInDisplayCutoutMode=shortEdges` (drawn into the camera cut-out, the page keeps clear of it with `env(safe-area-inset-*)`) and a dark window background. **The navigation bar kept coming back** (owner's screenshot: the three buttons on the right edge) because Capacitor's SystemBars plugin hides the bars only once at start and the default behaviour of a bar revealed by a swipe is to stay; so the workflow also writes its own `MainActivity` (`hideBars()` in `onResume` and `onWindowFocusChanged`, behaviour `BEHAVIOR_SHOW_TRANSIENT_BARS_BY_SWIPE`: a swipe from the edge shows the bars for a moment, then they go away again).
- **Google / Facebook sign-in opens the phone's browser.** Both refuse an app's embedded WebView, so the workflow adds the **@capacitor/browser** plugin (Chrome Custom Tab; `android/package.json`) and an intent filter `royalbilliard8://auth` on the activity (the page the browser ends on opens it to bring the game back to the front). Register `https://billiard8.onrender.com/auth/done` as a redirect address at Google (Web client) and Facebook (see the main README, "Start (sign-in) screen").
- **Which build is installed?** The workflow passes its `version_name (version_code)` to `tools/build_android.sh` as `APP_VER`, which injects `window.__APP_VER`: the start screen shows it in the bottom-right corner ("v 1.0.5 (14)") and Settings shows it at the bottom ("app 1.0.5 (14)", before the server build). No label = a build from before this was added.
- **HD pack is a must in the app.** The first-launch screen has no "Later" button while the HD pack downloads when the page runs inside the app (`window.__HD_BASE` is set); the web build keeps it. Only a **2G / 3G connection** skips it (`navigator.connection.effectiveType`); a weak phone or data saver on 4G / Wi-Fi still downloads it. A file that gets no byte for 30 s is dropped and retried (5 times, 2 s apart); a stalled but online phone keeps waiting, and the player is let in only when the phone is offline (or after the retries are used up) - the pack is tried again at the next start.
- New personal developer accounts must run a **closed test (about 12 testers for 14 days)** before production.
- HD pack: not bundled (Play base ~39 MB). On the first start the app downloads it (~51 MB) from the Cloudflare static site (`HD_BASE` in `tools/build_android.sh`, default `https://frosty-hill-615a.au7520384.workers.dev/`; its `_headers` sends `Access-Control-Allow-Origin: *` for `/hd/*` and `/assets.json`), with the same PUBG-style progress screen and the Settings switch. Test: `node tools/test_android_hd.js`. The HD files must be deployed there (they are, from `web/hd/`, after every push).

## Google Play Billing (the 💎 packs)
The app sells the six diamond packs - 100 / 250 / 500 / 1 000 / 2 500 / 5 000 💎 at $1.99 / $4.99 / $9.99 / $19.99 / $49.99 / $99.99 - as **consumable in-app products** whose ids are exactly `gems_100`, `gems_250`, `gems_500`, `gems_1000`, `gems_2500`, `gems_5000` (the same ids as the server's SKUs). The Capacitor plugin `@capgo/native-purchases` (pinned in `android/package.json`) opens Google's purchase window; the page finds the plugin by itself (`playOn()` in `index.html`).
How a purchase goes (`playBuy` / `playClaim` / `playRestore` in `index.html`, `POST /api/play/verify` + `GET /api/play/status` and `server/play.js` on the server):
1. The page asks the server (`/api/play/status`): can it verify a purchase at all? (If not, the Google window is never opened - nobody is charged.) The answer also carries this player's account tag, which goes to Google with the purchase.
2. Google's purchase window opens (`purchaseProduct`, no auto-acknowledge). The page gets a purchase token.
3. The page sends the token to the server. The server signs a service-account JWT, asks the **Google Play Developer API** (`purchases.products.get`) whether the token is a real, paid purchase of that pack made for this player's account, hands the 💎 over **once** (the same `fulfill()` grant as a card payment; the token's hash is the payment id, so a token never pays twice) and **consumes** the purchase (`purchases.products.consume`; if that fails it acknowledges, so Google does not refund it after 3 days).
4. The 💎 arrive with the next sync ("+250 💎 - Thank you for your purchase!").
Anything that stops half-way (the app was closed during the purchase, no internet, the server asleep, a slow payment method such as cash at a shop) stays at Google as an owned purchase; the page hands every owned purchase to the server again when the app starts (7 s after), when it comes back to the front, and when the shop's Money page / "Not enough diamonds" opens. The server pays what it has not paid yet and never pays twice.
Prices on the buttons are Google's own localized prices (`getProducts`).

### What you must do (once)
1. **Upload an .aab that contains the plugin to Play Console** (Internal testing track is enough). Play Console only lets you create in-app products after a bundle with the billing permission has been uploaded.
2. **Monetize → Products → In-app products → Create product**: six products with exactly these ids (an id cannot be changed afterwards) and these prices; set each one **Active**: `gems_100` $1.99, `gems_250` $4.99, `gems_500` $9.99, `gems_1000` $19.99, `gems_2500` $49.99, `gems_5000` $99.99. A merchant (payments) profile must be set up in Play Console.
3. **Let the server read the orders.** In Google Cloud (the project linked to Play Console) enable the *Google Play Android Developer API*, create a **service account** and a JSON key for it; in Play Console invite the service account's e-mail as a user (Users and permissions) with the permissions *View app information* and *Manage orders and subscriptions* for this app. (The screens move around now and then; Google's page "Getting started with the Google Play Developer API" has the current steps.)
4. **Put the JSON key into Render**: the game server service (billiard8.onrender.com) → Environment → `PLAY_SERVICE_ACCOUNT` = the whole JSON text (or the same text base64-encoded). It is a secret: never paste it in a chat or commit it. Optional: `PLAY_PACKAGE` (default `com.royalbilliard8.app`, the `appId` in `capacitor.config.json`).
5. **Test before you publish**: Play Console → Settings → License testing → add your Google account as a tester; install the app from the Internal testing link and buy a pack - testers are not charged. Check that the 💎 arrive and that you can buy the same pack again.
6. **Data safety form** (Play Console → App content): the app now also handles *purchase history* (the server keeps which pack was bought and a hash of Google's purchase token, to pay it once).
Not done yet (honest list): only the 💎 packs are sold in the app (coins come from the 💎 → 🪙 exchange); the whole flow was tested here against a fake Google and a fake plugin (`node server/test_play.js`, `node tools/test_play_ui.js`), NOT on a real phone with a real Play Console - the first real purchase is the real test.

### Refunds (taken back automatically)
When Google refunds or charges back a purchase, the server notices: every 30 minutes (and 90 s after a start) it reads `purchases.voidedpurchases` (the last 30 days) with the same service account, matches each voided purchase token to a delivery it made, and sends that player ONE `refund` grant (`take: <💎>`, never `gems`: only `fulfill()` may hand 💎 out): the app subtracts those 💎 (what the player already spent stays spent, the balance never goes below 0) and says "Google Play refunded the payment". The owner gets a bot message ("↩️ Google Play pulni qaytardi ..."). `GET /api/health` shows `play: {refundChecks, refunded, lastCheck, err}`. If `err` says 403, give the service account the Play Console permission to view financial data / orders (the exact permission name moves around in Play Console; this check has only been run against a fake Google). Tests: `node server/test_play.js` (48 checks, incl. refunds), `node tools/test_play_ui.js`.
